# 阶段5开发案例的安全筛选拒绝诊断

本报告仅解释四个已完成开发 trace：A 的六车 5201/5202，以及 B1、B2 的六车 5201。全部 `safety_rejected` 的已记录返回分支都是 `neighbor_reachable_occupancy`。B 的拒绝次数降低同时伴随送入 guard 的次数降低，非零执行次数没有增加，不能据此认定编队改善或选定方法。本分析不进入预登记选择评分，未读取 heldout，未运行控制器、物理积分或 SUMO，也未更改任何生产代码、参数或旧试验结果。

使用 `systematic-debugging` 与 `verification-before-completion` 技能进行只读定位和证据核验。主要产物为 [summary.json](/D:/yanjiu1/keyan1/results/phase5/guard_analysis_20260912T191212138298Z_de3c3f03/summary.json)、[脚本快照](/D:/yanjiu1/keyan1/results/phase5/guard_analysis_20260912T191212138298Z_de3c3f03/analysis_script.py)、[重放验证](/D:/yanjiu1/keyan1/results/phase5/guard_analysis_20260912T191212138298Z_de3c3f03/verification.json)。完整输入路径、SHA256、源码 SHA256、逐车统计、各车首个拒绝帧的自车状态与去除 ID 的可见邻车几何都保存在 summary。

每个案例均有 450 个已完成控制区间、2700 次车辆决策。guard attempt 严格定义为 `diagnostics.formation.prediction != null`，已逐条验证其等价于源码的 `abs(weight * raw_increment) > 1e-12`。非零执行定义为 `abs(applied_increment_mps2) > 1e-12`，并核对最终动作与基础 NOA 加速度之差。分母不能用所有车辆决策替代送入 guard 的次数。

四个案例均没有“guard 接受但 applied 为零”的记录，也没有 proposed 加速度被舒适/硬边界裁剪的记录。A/5201 的 v2、v3 各拒绝 440 次；A/5202 的 v1、v2、v4 各拒绝 440 次；B1、B2/5201 仅 v3 拒绝 440 次。B 的 v2 在 450 次决策中均无已选参考、没有送入 guard；A/5201 的同一离线车辆标签 v2 有 440 次尝试且全部被拒绝。这是两种方法拒绝计数差异的一项直接事实，不能把减少尝试描述成执行能力提高，也未通过额外反事实运行分离候选资格、排序与后续轨迹变化各自的效应。

非空 prediction 的实际结构在所有四个 trace 中都只有 `safe`、`reason`、`at_s`、`checked_s`。接受记录的 reason 是 `conditional_swept_prediction_clear`；所有拒绝记录的 reason 是 `neighbor_reachable_occupancy`。没有记录 `branch` 字段、触发拒绝的邻车标识、碰撞点、最小间距、扫掠递归深度或其他叶节点原因。`at_s` 是本次假设预测内部的相对时刻，不是试验绝对时刻，也不是已发生碰撞的时刻。

拒绝发生后，源码仅把 `formation_state` 改为 `FALLBACK`，同时保留可见参考、权重和缓存增量。下一拍仍先运行基础 NOA；本案例中基础行为均为 CRUISE/FOLLOW，因此这一状态标签本身不会阻止重新送检。所有发生拒绝的车辆都从 1.0 秒持续拒绝到 44.9 秒，每车 440 个连续拒绝决策。对应“输入记忆已经 FALLBACK、这拍再次拒绝”的计数分别为 878、1317、439、439；差额分别是首次进入 FALLBACK 的 2、3、1、1 辆车。没有把重复决策当成独立车辆样本。

参考切换没有使用逐帧物理 signature 元组不等来统计，因为参考正常运动也会改变位置。采用纯离线审计：将输出参考的完整位置、惯性速度、朝向、长宽与同帧 `record.initial` 逐字段匹配（绝对容差 1e−7），仅唯一匹配时赋予审计 actor alias；歧义和缺失必须记 unknown。此过程没有重新运行决策，也没有把标签传回控制器。四个案例的当前参考和相邻参考配对均无 unknown：A5201、B1/5201、B2/5201 均有 0 次已知切换；A5202 有 2 次，v3 在约 26.4 秒从 v2 切至 v1，v2 在约 32.5 秒从 v4 切至 v0。已建立参考后没有 null 释放事件；A 两例各获得 5 个参考，B 两例各获得 4 个参考。原始 signature 更新次数作为明确标记的非切换统计保留在 JSON 中。

源码核验明确了能够与不能够区分的范围。四个运行快照的 `noa/prediction.py`、`safety/geometry.py`、`models/kinematic.py` 哈希完全相同；分析针对运行自己的代码快照并与各自 code_hashes.json 校验，未依赖可能变化的工作区源码。predictor 在有限可见邻车的硬纵向加速度区间 −10 至 +5 m/s²、速度范围 0–33.3 m/s、登记的横向加速度界 0，以及车身 margin 0.15 m 下生成可达包络，然后对所有可见邻车做扫掠检查。所选编队参考只是其中一个可见目标，日志不提供实际导致拒绝的是哪一个目标。

`swept_collision` 的 True 至少合并了两个情况：端点/中点的包络重叠，以及达到最大递归深度后仍未能排除潜在相交。因此本证据支持“可达占位扫掠检查返回拒绝”，无法进一步断言是包络重叠还是未解决叶节点，也无法据此证明包络过保守。它更不证明真实车辆发生了碰撞。四个既有 validation 文件均报告 recording、driving、comfort 通过及几何碰撞/越界为 0；这是保留下来的既有结果，不能证明被拒绝的增量如果执行也会安全。

舒适加速度在送检前裁剪，jerk 在执行器动力学中限幅（登记值 2 m/s³），它们不是本次 `safe=False` 的独立返回原因。日志与源码足以排除“这批拒绝直接由某个 comfort/jerk 返回标签触发”的解释；但 jerk、执行器迟滞等仍影响预测运动，不能声称它们对可达占位结果没有间接影响。没有通过放宽界限、缩短预测时间或重新积分来尝试改善结果。
